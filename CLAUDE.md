# firepack — Claude instructions

Spec-driven Firestore + Flutter codegen. Pure Dart CLI. One YAML spec
(`firepack.yaml`) → models, repositories, providers, security rules,
indexes, storage paths, Mermaid graph.

## What this project is

- **Dart package + CLI**, not a Flutter app. SDK `^3.5.0`.
- Entry point: `bin/firepack.dart` (CommandRunner with subcommands
  `lint`, `viz`, `regen`, `diff`, `watch`).
- Library code in `lib/src/{spec,codegen,diff,viz}`.
- Tests in `test/`, fixtures in `test/fixtures/`.
- No Flutter, no Firebase SDKs as deps — firepack only *generates*
  Firestore/Flutter code, it doesn't depend on it.

## Bootstrap principle (read before adding features)

firepack is built **with** WorkBrief, not **for** WorkBrief. Don't add
speculative features. The rule:

1. WorkBrief hits a real pain (schema drift, rule audit, repo
   boilerplate, …).
2. firepack solves it generically.
3. WorkBrief consumes it.

If the user asks for a feature that doesn't have a real consumer pain
behind it, push back and point at `docs/PHILOSOPHY.md` (Non-Goals
table). Examples already on the no-list: sub-collections, multi-DB,
SQL backends, custom rule-DSL, migrations engine, drag-and-drop
editor.

## Workflow — use the justfile

The `justfile` is the canonical entrypoint for build/install/test:

| Recipe | Use |
|---|---|
| `just install` | `dart pub global activate --source path .` — install CLI globally |
| `just build` | compile `build/firepack` native binary |
| `just run <args>` | run from source without installing (e.g. `just run lint -s example/firepack.yaml`) |
| `just test` | full test suite |
| `just check` | format-check + analyze + test (CI-equivalent) |
| `just lint-example` / `just viz-example` | sanity-check toolchain on `example/firepack.yaml` |
| `just example-regen` | regenerate `example/lib/firepack/**` from `example/firepack.yaml` |
| `just example-analyze` | `flutter analyze` against the example app — proves generated code compiles |
| `just clean` | drop `.dart_tool/`, `build/`, `pubspec.lock` |
| `just distclean` | clean + global deactivate |

Don't paste raw `dart pub …` / `dart test` commands into chat when a
just recipe exists — it makes the workflow drift.

## Code conventions

- **Determinism first.** Every codegen output is sorted, stable,
  reproducible. Two runs on the same spec → byte-identical output.
  When touching a generator, add/extend a snapshot test in `test/`
  with a fixture under `test/fixtures/`.
- **Generated files carry a `// GENERATED by firepack`-style header**
  with the source spec path. Don't strip it.
- **Spec is the source of truth.** New field-types, new rule helpers,
  new generator targets — all start in `lib/src/spec/` (parser +
  model), then propagate outward.
- **No backwards-compat shims** for the spec format until pub.dev
  release. Bump `firepack: <n>` if breaking, document in
  `CHANGELOG.md`. Pre-1.0 — break freely.
- **CHANGELOG.md is hand-written, Keep-a-Changelog format**, German
  prose, every entry tied to a WorkBrief milestone. Match the tone of
  prior entries.
- Tests are plain `package:test`. Snapshot via string equality against
  fixture files.

## Don't

- Don't add Firebase / Flutter / Riverpod packages as deps. firepack
  emits code that uses them; it doesn't import them.
- Don't introduce `build_runner` / `freezed` / `json_serializable` —
  the whole point of firepack is to *replace* that fan-out.
- Don't refactor adjacent generators while fixing one. Surgical
  changes; one generator at a time. Each has its own snapshot test.
- Don't bump version in `pubspec.yaml` casually. Version bumps go with
  a CHANGELOG entry and a tagged WorkBrief consumption step.

## Pointers

- `docs/PHILOSOPHY.md` — bootstrap rule + Non-Goals table.
- `docs/ROADMAP.md` — milestone list, each tied to a WorkBrief pain.
- `docs/SPEC.md` — formal spec reference (v1).
- `example/` — self-contained Flutter + Riverpod app that consumes
  firepack itself. Spec at `example/firepack.yaml`, watch config at
  `example/firepack.config.yaml`, generated tree under
  `example/lib/firepack/**` (committed so `flutter analyze` works on
  a fresh clone). Hand-written: `lib/main.dart`,
  `lib/core/data/{firestore_paths,tenant_query}.dart`. Layout follows
  pub.dev convention (the `example/` dir IS the app). Exists as a
  compile-time smoke-test (wired into `just check`) and as an on-ramp
  for first-time readers. Regenerate via `just example-regen` after
  touching any generator. **Riverpod-only today**; Bloc support is a
  roadmap item, not a current feature.

## Open code-review findings (carry forward)

- **`firestore_paths.dart` codegen is missing.** README + repo
  generator both reference `paths.dart` as if it were generated, but
  no generator exists in `lib/src/codegen/`. The example app
  hand-writes the file as a stub. Real fix: add a
  `firestore_paths_generator.dart` mirroring the storage one, plus a
  `firepack regen --target paths` flow.
- **No Flutter smoke-test before this commit.** Codegens were only
  exercised via string-equality fixtures, so a generator could emit
  Dart that string-matched the fixture but didn't compile in a real
  Flutter app. The example app closes that loop; keep it green.
