# firepack example — Flutter + Riverpod, runnable on the Firebase Emulator

Minimal Flutter app that consumes firepack-generated code from
[`firepack.yaml`](./firepack.yaml) — the spec lives next to the app
that consumes it, exactly the shape a real firepack consumer ends up
with. Three reasons it exists:

1. **Compile-time smoke-test.** `flutter analyze` here is wired into
   `just check` at the repo root — if a generator change emits broken
   Dart, this app fails to analyse and the build goes red.
2. **Runnable PoC.** With the Firebase Emulator Suite the app launches
   end-to-end, no real Firebase project required.
3. **Open-source on-ramp.** Without a runnable example, "spec-driven
   codegen" is hard to grok. This shows the full path: spec → model →
   repository → Riverpod provider → UI.

## What's hand-written vs. generated

```
example/
├─ firepack.yaml                       ← the SPEC — single source of truth
├─ firepack.config.yaml                ← `firepack watch` targets
├─ firebase.json                       ← emulator config
├─ .firebaserc                         ← `demo-firepack` project alias
├─ firestore.rules                     ← GENERATED (deny-all today; the spec
│                                          declares no per-collection rules)
├─ firestore.emulator.rules            ← hand-written, permissive (emulator only)
├─ firestore.indexes.json              ← GENERATED
└─ lib/
   ├─ main.dart                        ← hand-written (UI + emulator wiring)
   ├─ core/data/
   │  ├─ firestore_paths.dart          ← hand-written stub (firepack TODO: codegen)
   │  └─ tenant_query.dart             ← hand-written (consumer-owned helper)
   └─ firepack/
      ├─ models/                       ← GENERATED — `firepack regen --target models`
      ├─ repositories/                 ← GENERATED — `firepack regen --target repos`
      └─ storage_paths.dart            ← GENERATED — `firepack regen --target storage`
```

Touching anything under `firepack/` directly is wrong — edit the spec
and regenerate. Everything else is fair game.

## Run it against the emulator

Prereqs: `firebase-tools` ≥ 15 and **JDK 21+** (the emulator's hard
requirement). `brew install openjdk@21` if you don't have it — the
justfile picks it up automatically without touching your system
default.

```bash
# Terminal 1 — start the emulator suite (Firestore + Auth + UI)
just example-emulator-up

# Terminal 2 — run the Flutter app against it
just example-run
```

The app opens in Chrome. You'll see "No posts yet" — click **Seed
demo data** to write 3 posts via the generated `PostRepository.add()`.
The list updates live through the generated `postWatchByOrgProvider`
stream. Watch the writes land in the Emulator UI at
<http://localhost:4000/firestore>.

### What you can do (CRUD)

Every action below routes through firepack-generated code — that's
the whole point of the demo. Open the Emulator UI alongside the app
to see each write land in real-time.

| Action | UI gesture | Generated code path |
|---|---|---|
| **Read** (list) | the screen, on load | `postWatchByOrgProvider` (`StreamProvider.family`) → `PostRepository.watchByOrg(orgId)` |
| **Create** (single) | FAB **New post** → fill form → **Create** | `PostRepository.add(Post)` + `Post.toJson()` |
| **Create** (batch) | empty-state **Seed demo data** | `PostRepository.add(...)` × 3 |
| **Update** | tap a tile → edit fields → **Save** | `PostRepository.updateById(id, fields)` (partial-update path, not overwrite) |
| **Delete** | trailing trash icon → confirm | `PostRepository.deleteById(id)` |

Two non-obvious touches worth noting:

- **Update uses `updateById` with a field-map**, not an `add`-overwrite.
  That demonstrates the partial-patch path through the generated
  repository — same shape `firepack` will keep emitting as the spec
  evolves.
- **New post IDs come from Firestore's auto-id generator**
  (`FirebaseFirestore.instance.collection('posts').doc().id`), then
  feed into the immutable `Post(id: ..., ...)` constructor. firepack
  and the underlying SDK coexist — it's not all-or-nothing.

## Why permissive emulator rules

`firestore.rules` is generated by firepack and reflects the spec — the
bundled blog spec declares no `rules:` blocks, so the generator emits
the safe deny-all default plus reusable helper functions. That's
correct behaviour but unusable in the emulator. `firebase.json`
therefore points at a hand-written `firestore.emulator.rules` that
allows everything for local dev. Real consumers add `rules:` blocks
to their spec and point `firebase.json` at the generated file.

## Why Riverpod (and not Bloc)

firepack today emits Riverpod providers because that's what its first
real consumer (WorkBrief) uses. Bloc is on the roadmap — same spec,
different generator target — but driven by a real consumer pain, not
speculatively. See `docs/PHILOSOPHY.md`.
